## Feasibility findings from this checkout

- The display is 240x160. The lower area is 240x48 (y=112..159).
  BG0 stores message, action and move pages at different vertical positions;
  action uses top 35 and move names top 55, with scrolling between pages.
- Four reference rows need at least 4x24=96px for name and metadata using the
  existing small font. A direct four-row transplant cannot fit the 48px region.
  Use two columns by two rows, 120x24 per card, with existing D-pad adjacency.
- The reference aesthetic does not require 3D: slanted borders, stepped color
  highlights, circles, and type badges can be ordinary 4bpp BG0 tiles. Avoid
  claiming that smooth reference gradients or dual-screen proportions survive
  conversion unchanged.
- Four move cards can use 15x3 tiles each (180 tiles total). A candidate contiguous
  allocation is 0x300..0x3B3, within the 10-bit BG tile index. This overlaps the
  current move-description allocation at 0x350, which must be relocated before
  integration. Current PP/type windows also must be suppressed/replaced rather
  than allowed to overwrite the new cards.
- BG palettes 2..4 belong to scenery; 5 to existing text; 8..11 are used for
  battler graphics/effects. Candidate card palettes 12..15 require explicit
  load-on-menu-entry and a lifecycle audit across bag/party returns and animation.
  Do not assume that an unused-looking bank is globally free.
- Existing action/move cursor functions directly write fixed tilemap positions.
  They must be changed with the layout, including move reordering and cancel.
- Dynamic types, Dynamax names, Z-Move descriptions, PP, effectiveness, and
  description toggles already have controller behavior. Preserve that behavior
  while changing presentation; static mockup strings do not prove integration.

## Implementation

### Current implementation checkpoint

`src/sm_battle_menu.c` owns the XY lower UI. `BattleInitBgsAndWindows` clones
the normal templates for XY; standard styles keep the original templates.
Action is a 30x6 canvas at (0,34), base 0x190, palette 12. The four moves are
15x3 windows at (0/15,54/57), bases 0x300 + slot*45, palettes 12..15.
The message window is 30x6 at (0,14), base 0x90, palette 13. All full lower
windows cover y=112..159 on their respective scrolling page.

The gray description panel is 30x10 at (0,44), base 0x170, palette 6, displayed
at y=32..111 above the move cards. It deliberately reuses the hidden action
page's tile storage; returning to actions redraws that page. It does not overlap
the four live move buffers. Closing details clears its tilemap without drawing
an offscreen standard border at x=-1.

The player controller routes direction keys spatially around the asymmetric
buttons. Battle text/cursor hooks redraw cards without changing move selection
or command emission. `SmBattleMoveType` factors the prior controller logic so
per-card type labels share the existing Tera/Ogerpon/Max/dynamic-type rules.
Card highlights derive from the existing type RGB values. Max names are used
on cursor redraw too. Z views get separate title/effect and metadata cells;
their title/PP/type presentation was checked in a display fixture. Original tiny action symbols are
generated by real Aseprite and embedded as four 16x16 4bpp assets.

Safari/catch tutorial/Pokedude and non-normal window modes retain their original
lower templates. This guard was added after the initial cached-ROM session;
special-mode runtime checks remain pending.

The party footer and popups use dark teal with white text. No-PP requests are
respected on all cards. The action center retains the existing partner preview.
For the optional pre-Gen-IV reorder setting, the source card has a gold border
and SWAP label, while the target cursor stays cyan; the original PP-pane prompt
is suppressed because it would overlap the new cards. Current configuration
keeps battle move reordering disabled, as before.

### Six-card party implementation checkpoint

In-battle SINGLE/DOUBLE party layouts use six 15x4 windows at x=0/120,
y=0/40/80. Each card is 120x32 with an 8px vertical gap. This fits the existing
font, icon, level/status, gender and HP data without displacing the footer.
The discarded 15x5 candidate required more intrusive tile allocation changes.
Cards occupy 0x63..0x1CA. Existing windows at/after 0x1C7 shift by 0x20,
including dynamic prompts, cancel/confirm, and yes/no; all stay below tile 0x400.

`src/party_menu.c` selects custom information rectangles, sprite coordinates,
rounded white/green card drawing, pink fainted cards and cyan selected edges.
HP/gender palette entries retain their existing producers. Direction handling
follows the 2x3 geometry and preserves the existing selection/eligibility tasks.
Outside these in-battle layouts the original party UI remains selected.

BG1 uses tiles 1 and 2 for its green patterned background. Tile 0 MUST remain
transparent: BG2's empty map uses the same character block and would otherwise
cover all cards and sprites. This was diagnosed and fixed during runtime testing.

`tools/mgba_live/sm_party_fixture.py --elf <matching-debug.elf>` generates the
six-slot RAM fixture (optional `--double`). It resolves addresses from the ELF
and correctly writes the encrypted 11th/12th nickname characters plus checksum.
Do not write an EOS at box offset 18: it is the language/nature byte.

menus together. DEFAULT uses the original battle and party layouts. The new
menus do not introduce save fields or change combat rules. Original reference
photos are not included; editable Aseprite studies and original icons are.

The normal ROM is `pokeemerald.gba`. `evidence/review/final-*.png` shows the
matching final debug build; `design/` preserves early layout studies and is not
