# Generation VII-inspired lower battle UI

Status: integrated on `feature/ui-style-switch-20260909`, with normal/debug
builds, the UI-style save test, and mGBA checks. See `test_plan.md` for exact
screens, build hashes, display-fixture boundaries, and untested special modes.

## Request and references

Restyle the entire lower battle area: action selection, move selection, message
frame, and move details. Preserve the reference colors and decoration; adaptation
is allowed after checking feasibility. Keep the existing upper XY HUD and the
DEFAULT/XY selection behavior.

Viewed local Taildrop originals under the engram-mcp reference incoming directory:
`IMG_2961.jpg` (single move selection), `IMG_2962.jpg` (double move selection),
`IMG_2963.jpg` (gray move detail panel), ingested 2026-09-09. These are visual
references, not redistributed assets. They show a teal field with circular line
motifs, dark diagonal card edges, type-colored highlights, compact type badges,
PP on each card, and a slate-gray detail panel.

Additional user attachments `1-写真1.jpg` and `2-写真2.jpg` specify action and
party selection. Action layout must preserve the reference hierarchy: large red
FIGHT on the right, green POKEMON above gold BAG on the left, blue RUN below
the center, and teal circular decoration between them. The two-by-two adaptation
applies to move cards, not the action buttons. Party selection is also in scope:
green field, six white rounded cards in two columns, red fainted-state treatment.
Its separate GBA menu may use the whole 240x160 screen.

## Feasibility findings from this checkout

- The display is 240x160. The lower area is 240x48 (y=112..159).
  BG0 stores message, action and move pages at different vertical positions;
  action uses top 35 and move names top 55, with scrolling between pages.
- Four reference rows need at least 4x24=96px for name and metadata using the
  existing small font. A direct four-row transplant cannot fit the 48px region.
  Use two columns by two rows, 120x24 per card, with existing D-pad adjacency.
- The reference aesthetic does not require 3D: slanted borders, stepped color
  highlights, circles, and type badges can be ordinary 4bpp BG0 tiles. Avoid
  claiming that smooth reference gradients or dual-screen proportions survive
  conversion unchanged.
- Four move cards can use 15x3 tiles each (180 tiles total). A candidate contiguous
  allocation is 0x300..0x3B3, within the 10-bit BG tile index. This overlaps the
  current move-description allocation at 0x350, which must be relocated before
  integration. Current PP/type windows also must be suppressed/replaced rather
  than allowed to overwrite the new cards.
- BG palettes 2..4 belong to scenery; 5 to existing text; 8..11 are used for
  battler graphics/effects. Candidate card palettes 12..15 require explicit
  load-on-menu-entry and a lifecycle audit across bag/party returns and animation.
  Do not assume that an unused-looking bank is globally free.
- Existing action/move cursor functions directly write fixed tilemap positions.
  They must be changed with the layout, including move reordering and cancel.
- Dynamic types, Dynamax names, Z-Move descriptions, PP, effectiveness, and
  description toggles already have controller behavior. Preserve that behavior
  while changing presentation; static mockup strings do not prove integration.

## Implementation

### Current implementation checkpoint

`src/sm_battle_menu.c` owns the SM lower UI. `BattleInitBgsAndWindows` clones
the normal templates for `BATTLE MENU: SM`; DEFAULT keeps the original templates.
Action is a 30x6 canvas at (0,34), base 0x190, palette 12. The four moves are
15x3 windows at (0/15,54/57), bases 0x300 + slot*45, palettes 12..15.
The message window is 30x6 at (0,14), base 0x90, palette 13. All full lower
windows cover y=112..159 on their respective scrolling page.

The gray description panel is 30x10 at (0,44), base 0x170, palette 6, displayed
at y=32..111 above the move cards. It deliberately reuses the hidden action
page's tile storage; returning to actions redraws that page. It does not overlap
the four live move buffers. Closing details clears its tilemap without drawing
an offscreen standard border at x=-1.

The player controller routes direction keys spatially around the asymmetric
buttons. Battle text/cursor hooks redraw cards without changing move selection
or command emission. `SmBattleMoveType` factors the prior controller logic so
per-card type labels share the existing Tera/Ogerpon/Max/dynamic-type rules.
Card highlights derive from the existing type RGB values. Max names are used
on cursor redraw too. Z views get separate title/effect and metadata cells;
their title/PP/type presentation was checked in a display fixture. Original tiny action symbols are
generated by real Aseprite and embedded as four 16x16 4bpp assets.

Safari/catch tutorial/Pokedude and non-normal window modes retain their original
lower templates. This guard was added after the initial cached-ROM session;
special-mode runtime checks remain pending.

The party footer and popups use dark teal with white text. No-PP requests are
respected on all cards. The action center retains the existing partner preview.
For the optional pre-Gen-IV reorder setting, the source card has a gold border
and SWAP label, while the target cursor stays cyan; the original PP-pane prompt
is suppressed because it would overlap the new cards. Current configuration
keeps battle move reordering disabled, as before.

### Six-card party implementation checkpoint

In-battle SINGLE/DOUBLE party layouts use six 15x4 windows at x=0/120,
y=0/40/80. Each card is 120x32 with an 8px vertical gap. This fits the existing
font, icon, level/status, gender and HP data without displacing the footer.
The discarded 15x5 candidate required more intrusive tile allocation changes.
Cards occupy 0x63..0x1CA. Existing windows at/after 0x1C7 shift by 0x20,
including dynamic prompts, cancel/confirm, and yes/no; all stay below tile 0x400.

`src/party_menu.c` selects custom information rectangles, sprite coordinates,
rounded white/green card drawing, pink fainted cards and cyan selected edges.
HP/gender palette entries retain their existing producers. Direction handling
follows the 2x3 geometry and preserves the existing selection/eligibility tasks.
Outside these in-battle layouts the original party UI remains selected.

BG1 uses tiles 1 and 2 for its green patterned background. Tile 0 MUST remain
transparent: BG2's empty map uses the same character block and would otherwise
cover all cards and sprites. This was diagnosed and fixed during runtime testing.

`tools/mgba_live/sm_party_fixture.py --elf <matching-debug.elf>` generates the
six-slot RAM fixture (optional `--double`). It resolves addresses from the ELF
and correctly writes the encrypted 11th/12th nickname characters plus checksum.
Do not write an EOS at box offset 18: it is the language/nature byte.

## Handoff

Select `OPTION > BATTLE MENU > SM` for the new action, move, message, detail and
in-battle party menus. Select DEFAULT to return those screens to the original
layout. `UI STYLE: DEFAULT / XY` now independently controls the upper HUD.
New games and unknown battle-menu values default to the original menus.

The saved `optionsBattleMenu` field uses the former 16-bit alignment padding at
SaveBlock2 +0x16. The existing options word at +0x14, Pokedex at +0x18 and later
data keep their offsets. Option scrolling exposes all nine rows without reducing
font size; B and CANCEL apply changes through the existing options save path.
Normal in-game SAVE persists the selection. Combat rules are unchanged.
Original reference photos are not included; editable Aseprite studies and
original icons are.

## Palette and interaction refinement — 2026-09-09

The original dark move rows initially became a white name row and pale
type-tinted metadata row. Both rows now use the move type color, surrounded
by opaque mint. Type badges retain a dark
type color and white lettering; PP uses navy, with dark red for zero. Focus uses
emerald teal, and Z pages use cream with gold rules. Action panels retain their
asymmetric placement, with layered borders, diagonal color sweeps, top highlights,
gold focus corners and a separate FIGHT nameplate/flame-ray decoration. The
center includes the actor and CHOOSE ACTION or the partner move preview.

Key RGB555 colors are: opaque mint `(24,30,26)`, move ink `(1,3,5)`,
general ink `(3,8,9)`, teal focus `(3,19,17)`, gold `(31,26,12)`, and party background
`(17,25,15)` with lighter `(21,28,18)` diagonal details. Palette index 0 remains
transparent on GBA BGs regardless of its RGB value; canvases use index 11 to
avoid black holes in the action center and between move cards.

Z selection previously relied only on `zmove.viewing`, which the controller
clears before target selection. Effectiveness updates could then repaint an
ordinary move card over part of the Z page. `sZDisplay` now retains the displayed
page until the controller redraws normal move names or actions. It does not
change the controller's selected gimmick, target, PP or emitted command.

The normal ROM is `pokeemerald.gba`. `evidence/polish/` shows this refinement;
`evidence/review/` is the earlier implementation. `design/` preserves early layout studies and is not
a screenshot of final runtime output. See the test plan before extending this
layout to additional special battle/party modes or translated fonts.

## Full-card type colors — 2026-09-09

The move reference images IMG_2961/IMG_2962 use the type hue across each
card, including the move name. For each RGB555 type component `c`, the title
now uses `(c + 62) / 3` and the metadata surface uses `(c + 31) / 2`.
The title is a lighter highlight of the same hue; small text uses darker ink.
The shared mint surround, 2x2 layout, type badge, zero-PP red, empty slots,
Z page treatment and independent BATTLE MENU option remain unchanged.
`evidence/type-colors/` captures all 18 ordinary types and Stellar Tera Blast,
plus the reference's Metal Claw/Magnitude/Astonish/Bulldoze combination.

## SM move information sheet with type colors — 2026-09-09

The move-detail reference IMG_2963 uses a swept sheet with move identity on
the left, category/power/accuracy on the right and description below. The
previous blue panel with one compressed CAT/PWR/ACC line is replaced by that
information hierarchy inside the existing 240x80 overlay. The left column
shows the resolved move name, current/max PP and dynamic type badge. The right
column retains the existing category sprite and power/accuracy producers.
Max move names/descriptions and power still come from the controller.

Following the requested final adjustment, the sheet uses the selected type's
hue rather than a shared gray or blue. For RGB555 type component `c`, the
body is `(c+3)/4`, alternating stats band `(c+5)/3`, rim `(c+10)/2`, edge
highlight `(c+31)/2` and badge `(c+62)/3`. White text and pale red zero PP
remain readable on these dark surfaces. The shallow swept upper/lower edges,
row bands and column divider evoke the reference without consuming more tiles.

The renderer owns palette 6; the four move cards retain palettes 12..15.
No new assets, save fields, battle rules or inputs are introduced. L or B
closes details through the existing controller; D-pad refreshes the selected
move and its palette. BATTLE MENU DEFAULT retains the original detail layout.
Its numeric buffers now reserve four bytes for three digits plus EOS.
`evidence/details/` contains matching-ROM captures and the test plan records
the fixture limits.
